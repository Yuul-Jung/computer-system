프로그램과 명령어

3장 · 2 / 10

명령어(instruction)는 CPU가 한 번에 하는 일 하나다. "레지스터 두 개를 더하라", "이 주소에서 값을 읽어라" 같은 아주 작은 일이다. 프로그램은 이 명령어들을 순서대로 늘어놓은 것이다. CPU는 자신의 ISA에 맞는 기계어를 해독·실행한다. C 소스는 컴파일러와 어셈블러를 거쳐 기계어로 변환되며, 컴파일 옵션과 최적화에 따라 명령어가 달라질 수 있다.

단계누가 읽나특징
C 소스사람CPU 종류와 거의 무관하다. 한 줄이 명령어 여러 개가 된다.
어셈블리어사람(+어셈블러)ISA별 명령어의 문자 표현. li·ret처럼 실제 명령어로 확장되는 의사 명령어도 있다.
기계어CPURV32I 기본 명령어는 32비트이며, C 확장을 활성화하면 16비트 압축 명령어도 사용한다.
핵심명령어의 종류와 형식을 정한 약속을 명령어 집합 구조(ISA, Instruction Set Architecture)라 한다. MicroBlaze V는 RISC-V 기반 32비트 프로세서로, RV32IMC를 포함한 다양한 ISA 구성을 지원한다.

소스파일 — 사람이 쓰는 프로그램

3장 · 3 / 10

소스파일은 텍스트 파일이다. 실습에서는 .c(실제 코드)와 .h(헤더 — 다른 파일과 공유할 이름·주소·함수 선언)를 쓴다. 아래는 LED 16개를 한 칸씩 회전시키는 C 프로그램이다. 주소 0x4000_0000은 설명용 예시이며, 실제 Vivado Address Editor의 AXI GPIO 베이스 주소와 연결 구성을 확인해야 한다. 이 장의 나머지 페이지는 이 코드가 빌드되어 실행되는 과정을 다룬다.

#include <stdint.h>

/* 레지스터 직접 접근 매크로 (soc_map.h와 같은 방식) */
#define REG32(a)   (*(volatile uint32_t *)(a))
#define GPIO_LED   0x40000000u        /* 예시: AXI GPIO 채널 1 데이터 레지스터 */

uint32_t pattern = 0x01;              /* 초기값 있음 → .data */
uint32_t count;                       /* 초기값 없음 → .bss  */

/* 바쁜 대기: n번 세는 동안 시간을 보낸다 */
static void delay(volatile uint32_t n)
{
    while (n--)
        ;
}

int main(void)
{
    /* (추가) AXI GPIO 채널 1 TRI: 0은 출력, 1은 입력 */
    REG32(GPIO_LED + 4u) = 0u;

    for (;;) {
        REG32(GPIO_LED) = pattern;                      /* LED에 현재 패턴 출력 */
        pattern = (pattern << 1) | (pattern >> 15);     /* 한 칸 왼쪽으로 회전 */
        pattern &= 0xFFFF;                              /* LED 16개만 사용 */
        count++;                                        /* 몇 번 돌았는지 */
        delay(1000000);
    }
}
파일담는 것우리 SoC 예
.c함수 본문, 변수main.c, uart.c, timer.c
.h주소 상수, 함수 선언soc_map.h(주소맵), uart.h
보드 연결AXI GPIO 채널 1을 LED 출력에 연결한 예시다. IP의 포트 연결·실제 주소·출력 방향이 맞아야 켜진다. volatile은 MMIO 쓰기 최적화를 방지하며, 단순 지연 루프는 정확한 시간을 보장하지 않는다. 실제 실행에는 Vitis의 시작 코드·링커 설정이 필요하다.

빌드 과정 — 소스에서 실행파일까지

3장 · 4 / 10

소스파일을 실행파일로 만드는 일을 빌드(build)라 한다. 개념적으로 네 단계로 나뉜다. .i와 .s는 생성 과정을 보여 주는 중간 파일이며, 일반 빌드에서는 별도 파일로 남지 않을 수 있다. 다른 CPU용 프로그램을 PC에서 만드는 컴파일러를 크로스 컴파일러(cross compiler)라 하며, MicroBlaze V용 Vitis 툴체인에는 RISC-V 교차 컴파일러가 포함된다. 도구 실행 파일명은 설치·프로젝트 구성에 따라 다르므로 실제 빌드 로그를 확인한다.

단계입력 → 출력하는 일
전처리.c → .i#include 파일을 끼워 넣고 #define을 글자 그대로 바꾼다
컴파일.i → .sC를 RISC-V 어셈블리어로 번역한다
어셈블.s → .o어셈블리어를 기계어로 바꾼다. 외부 심볼 참조는 재배치 정보로 남을 수 있다
링크.o 여러 개 → .elf파일들을 합치고, 링커 스크립트대로 주소를 정하고, 빈 주소를 채운다

어셈블리어 — 명령어를 글자로

3장 · 5 / 10

어셈블리어는 CPU 명령어를 사람이 읽도록 표현한 것이다. 앞의 단어가 무슨 일을 할지(연산), 뒤의 이름과 숫자가 무엇을 가지고 할지(오퍼랜드)를 나타낸다. 아래는 C 함수와 RV32IMC 대상으로 컴파일한 어셈블리어를 나란히 놓은 것이다. 의사 명령어는 실제 기계어로 바뀌며, 최적화 설정에 따라 표현이 달라질 수 있다.

C 소스

void led_on(void)
{
    REG32(0x40000000u) = 0xFF;   /* 예시 주소의 LED 하위 8개 켜기 */
}

어셈블리어

led_on:
    lui  a0, 0x40000      # a0 = 0x4000_0000 (상위 20비트)
    li   a1, 0xff         # a1 = 0xFF
    sw   a1, 0(a0)        # 메모리[a0 + 0] ← a1  (32비트 쓰기)
    ret                   # 호출한 곳으로 돌아가기
명령어뜻왜 필요한가
luiLoad Upper Immediate — 상위 20비트에 값 넣기이 예시 주소는 하위 12비트가 0이므로 LUI 한 명령어로 만든다
liLoad Immediate — 상수 적재 의사 명령어이 값은 실제로 addi a1, zero, 255로 인코딩된다
swStore Word — 32비트를 메모리에 쓰기주소 0x4000_0000에 쓰면 메모리가 아니라 GPIO가 받는다
retReturn — 함수에서 돌아가기의사 명령어로, RV32IMC에서는 c.jr ra로 압축될 수 있다
SoC 연결REG32()로 주변장치를 읽거나 쓰는 기본 코드는 lw(읽기)와 sw(쓰기) 등으로 구현된다. 주변장치 제어에 전용 I/O 명령어가 필요하지 않다.

기계어 — 메모리에 놓인 숫자

3장 · 6 / 10

어셈블러는 각 명령어를 정해진 비트 형식의 숫자로 바꾼다. RISC-V의 C 확장은 압축(Compressed) 명령어로, 자주 쓰는 명령어를 16비트로 줄여 프로그램 크기를 줄인다. C 확장이 활성화되면 코드에 4바이트·2바이트 명령어가 섞일 수 있다. C 확장을 비활성화한 RV32I 구성에서는 아래 압축 명령어를 사용하지 않는다.

lui a0, 0x40000의 기계어 0x4000_0537을 비트로 나누면
비트 31~120x40000즉시값(Immediate)넣을 상위 20비트
비트 11~701010 = 10rd (목적지 레지스터)x10 = a0
비트 6~00110111opcode (연산 코드)LUI
핵심메모리 바이트 37 05 00 40은 리틀 엔디안으로 조합하면 0x4000_0537이다. li와 ret은 의사 명령어이고, c.sw와 c.jr은 C 확장에 속한다. 명령어의 비트 구조는 4장에서 자세히 본다.

링커 — 파일들을 하나로 잇기

3장 · 7 / 10

소스파일을 여러 개로 나누면, 한 파일에서 다른 파일의 함수를 부를 때 해당 함수의 최종 배치 주소가 아직 결정되지 않을 수 있다. 그래서 오브젝트 파일에는 uart_putc를 참조하는 명령어와 재배치 정보(Relocation)를 남길 수 있다. 링커가 모든 오브젝트 파일을 모아 주소를 정한 뒤 이 자리를 채운다.

링크 전 (main.o)

li    a0, 0x41        # 'A'
auipc t1, 0x0         # R_RISCV_CALL_PLT uart_putc
jr    t1              #   ← 링크 전 외부 심볼 참조

링크 후 (app.elf)

li    a0, 0x41        # 'A'
j     0x6 <uart_putc> #   ← 링크 후 대상 주소가 확정
SoC 연결main.o에서 uart_putc를 참조하고 uart.o에서 구현하면 링커가 연결한다. 위 코드의 j 0x6은 Clang 17·LLD로 만든 별도 최소 예제를 실제 확인한 값이다. 주변장치 드라이버를 파일별로 분리할 때도 같은 원리를 쓴다.

실행파일 ELF — 기계어와 설명서

3장 · 8 / 10

링커의 결과물은 ELF(Executable and Linkable Format) 파일이다. 기계어만 들어 있는 것이 아니라 "어떤 CPU용인지, 어느 주소에 놓을지, 함수 이름은 무엇인지" 같은 설명이 함께 들어 있다. 아래 그림은 ELF의 주요 정보와 섹션을 개념적으로 나타낸 것이다. .text 등의 정확한 주소·크기·시작 주소는 빌드 옵션, 시작 코드, 링커 스크립트에 따라 달라진다.

섹션주소크기들어 있는 것파일에 내용이 있나
.text링커 결정빌드별 상이main, _start(시작 코드)있음
.data링커 결정예: 4 Bpattern = 0x01있음
.bss링커 결정예: 4 Bcount없음 — 크기만 기록, 시작할 때 0으로 채움
핵심소스 코드 위치에 중단점을 연결하려면 보통 -g로 생성한 디버그 정보가 필요하다. 심볼과 디버그 정보는 ELF에 포함될 수 있지만 일반적으로 CPU가 실행할 BRAM 초기화 데이터에는 포함되지 않는다. .bss는 실행 초기화 과정에서 0으로 설정한다.

메모리 배치 — 링커 스크립트

3장 · 9 / 10

각 섹션을 메모리 어디에 둘지는 링커 스크립트가 정한다. Vitis에서는 하드웨어 플랫폼의 메모리 맵을 토대로 lscript.ld를 생성·편집할 수 있다. 아래는 BRAM을 0x0000_0000부터 64 KB로 설정한 교육용 메모리 배치다. 실제 주소·크기는 Vivado Address Editor와 Vitis 링커 설정을 기준으로 확인한다.

메모리 배치를 설명하는 축약 링커 스크립트 (실행용 원본 대체 불가)

MEMORY {
    lmb : ORIGIN = 0x00000000, LENGTH = 64K     /* BRAM 64 KB */
}
SECTIONS {
    .text : { *(.text*) *(.rodata*) } > lmb      /* 기계어 · 상수 */
    .data : { *(.data*) *(.sdata*)  } > lmb      /* 초기값 있는 변수 */
    .bss  : { *(.bss*)  *(.sbss*) *(COMMON) } > lmb  /* 초기값 없는 변수 */
    _stack_top = ORIGIN(lmb) + LENGTH(lmb);      /* 스택 시작 위치 심볼만 정의 */
}
주의링커는 .text·.data·.bss 등의 정적으로 배정된 섹션이 메모리 영역을 초과하면 오류를 낼 수 있다. 그러나 이 축약 스크립트에는 스택·힙의 실제 공간 예약과 시작 코드가 빠져 있어, 실행 중 스택·힙 충돌까지 검사하지 못한다. 실제 Vitis 프로젝트에서는 스택·힙 크기와 리셋 시작 주소도 함께 설정해야 한다.

적재와 실행 · 3장 정리

3장 · 10 / 10

ELF의 실행 대상 세그먼트를 BRAM 등 실행 메모리에 적재하면 CPU가 명령어를 인출할 수 있다. 개발할 때는 JTAG 디버거가 소프트웨어를 내려받고, 독립 부팅에서는 UpdateMEM으로 ELF의 BRAM 초기화 내용을 FPGA 비트스트림에 반영한 뒤 QSPI에 기록한다. 실제 적용 여부는 Vivado 구현·메모리 구성에 따라 달라진다.

이번 장 개념한 줄 정리우리 SoC에서
명령어 · ISACPU가 한 번에 하는 일 · 그 약속RV32I 기반 (M/C 확장 선택 가능)
소스파일사람이 쓰는 .c · .hmain.c, soc_map.h
빌드전처리 → 컴파일 → 어셈블 → 링크Vitis Build
기계어32비트 · 16비트(압축) 숫자37 05 00 40 = lui
링커파일을 합치고 주소를 채움lscript.ld
ELF기계어 + 적재 정보 + 심볼.text · .data · .bss
적재ELF를 메모리에 옮김JTAG 다운로드 · UpdateMEM + QSPI (구성 시)
공식 절차AMD UG1580 · UpdateMEM — ELF 데이터와 BRAM 위치 정보를 이용해 FPGA 구성 이미지의 초기값을 갱신한다. QSPI에 ELF 파일만 복사한다고 CPU가 자동 실행하는 것은 아니다.
